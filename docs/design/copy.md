# 對外文案

介面上所有面向使用者的文字都適用，包含主辦單位工作區這類內部工具。視覺與版面規則在 [`DESIGN.md`](../../DESIGN.md) 與[元件與介面規格](./components.md)。


對外文案採**最少必要資訊**，預設是少寫。一件事實不會因為它為真、資料模型裡有、方便稽核、技術上相關或容易解釋，就該被顯示。決策脈絡見 [ADR-0024](../adr/0024-user-facing-copy-uses-minimum-necessary-disclosure.md) 與 [ADR-0036](../adr/0036-provenance-labels-name-the-source-not-its-trust-level.md)。

只顯示能實質幫助使用者做到下列其中一件事的資訊：

- 理解自己正在看什麼；
- 做出決定；
- 執行一個動作；
- 理解一項重要的限制或後果。

**The Removal Test.** 刪掉一句話後，如果使用者的理解與行動都沒有改變，就刪掉它。

### Values Over Explanations

用精簡標籤與事實值，不用解釋性散文。

- **可以：** `主辦單位`、`Fancy Frontier 47`、`匯入 2026.08.21`、`原始來源`、`由社團填寫`、`最後更新 2026.08.27`。
- **不可以：** `此資料來自主辦單位，可供核對`、`此內容由社團本人自行提供`、`本站尚未驗證此資料`、`點擊此處可查看原始資料來源`。

版面結構、標籤、連結與日期本身就要把這些事實講完，不另外附加說明。

### Plain Words, No Programming Knowledge

介面文案一律假定讀者沒有任何程式設計知識，主辦單位工作區這類只有少數人使用的內部工具也一樣——使用它的是活動主辦人員，不是工程師。

把資料模型、版本控制與流程實作的詞彙翻成使用者自己的話：

- **可以：** `編輯中`、`待修正清單`、`第 3 版`、`活動代碼`、`場地 ID`、`工作表`、`負責人`、`協作者`。
- **不可以：** `引導中`、`目前阻擋項`、`Revision 3`、`eventId`、`Venue-space ID`、`Worksheet`、`Owner`、`Editor`、`scope`、`mapping`、`metadata`、`immutable`、`API`。

翻譯是換詞，不是加解釋：`儲存` 取代 `儲存 revision`，而不是改寫成一段說明版本紀錄如何運作的散文。欄位意義真的看不出來時，一行短句就夠。

技術詞彙留在程式碼、型別、契約文件與 `CONTEXT.md`，不出現在畫面上。

**驗證模組不是文案的出處。** 一個驗證函式若同時服務兩個控制面，它知道的必然比任一控制面少——地圖驗證只有攤位代碼，沒有活動日名稱、沒有場地名稱、也不知道匯入檔叫什麼。它回的 `code` 與結構化欄位（例如攤位代碼、數量）才是共用的部分，**句子由呈現端各自寫**，寫在那個控制面唯一的翻譯點上，讓同一個控制面的每一處都拿到同一句。模組自己仍要留一句能看的話，給沒有更好脈絡的呼叫端用；那句同樣不得印出內部識別字。

### Audience and Task Boundaries

同一項資訊是否需要顯示，取決於**目前的操作角色與任務**，不是帳號本身擁有多少權限。管理者進入社團填寫流程時仍使用社團文案；主辦在檢查匯入資料時，檔名、列號與攤位代碼若能直接幫助修正，就屬於必要資訊。

| 面向 | 文案先回答 | 通常需要 | 預設省略 |
|---|---|---|---|
| 一般使用者／讀者 | 這是什麼、在哪裡、有哪些內容 | 活動、日期、場館、攤位、社團、頒布資訊、必要分級、會影響判讀的來源與更新日期 | 匯入流程、審核歷程、內部版本、系統驗證與維運說明 |
| 社團 | 我要填什麼、是否儲存、什麼會公開 | 欄位用途、必要範例、儲存與公開結果、需要修正的項目、刪除或保留的實際影響 | 認證實作、資料表、同步流程、與填寫無關的可信度評論 |
| 主辦單位 | 準備到哪裡、哪裡有問題、去哪裡修正 | 活動日、場地、攤位代碼、問題數量、必要的來源檔／列號、修正入口、送審與發布結果 | 儲存常數、資料結構名稱、系統自動產生且不需操作的識別字 |
| 系統管理者 | 影響什麼、能怎麼處置、失敗在哪裡 | 操作對象、權限、審核／發布狀態、影響範圍、必要時間與診斷識別資訊 | 整包原始回應、敏感憑證、沒有處置用途的內部資料 |

這張表是資訊邊界，不是要求四套獨立文案系統。共用狀態與動作仍使用同一個領域詞彙；只有脈絡與可採取的動作不同時才分流。

**管理者不是工程師模式。** 管理者做審核、權限或發布操作時仍先用業務語言。只有在實際排錯，而且錯誤代碼、階段或識別字能幫助定位問題時，才顯示必要的診斷資訊；不要因為使用者有管理權限就直接傾倒內部資料。

### Action and State Accuracy

文案提到的動作必須真的可執行，而且符合目前權限與狀態。沒有建立權限的人不能被引導去「建立活動」；沒有可重試動作時不要寫「重新嘗試」；「前往修正」必須能到達可修正的位置。

狀態名稱描述實際結果，不用模糊的「完成」代替不同階段。尤其區分：

- **儲存**：內容已保存，不代表已送審或公開。
- **送審**：內容已交付審核，不代表已核准。
- **核准**：審核通過，不代表已發布。
- **發布**：內容已進入公開狀態。

如果一個畫面需要同時說明兩個狀態，直接說結果，例如「已儲存，尚未公開」，不要讓使用者從流程實作推測。

錯誤訊息優先回答**哪裡發生什麼問題**，再提供當下可採取的修正動作。相同問題在同一控制面應共用核心描述；側欄摘要可以比詳細問題卡短，但不能換成另一種意思。

### Internal Process Stays Internal

除非使用者需要，否則不呈現內部或維運中繼資料：驗證流程、審核狀態、匯入方法、同步細節、內部 provenance 術語、信心或信任標籤、維護責任歸屬、實作細節與資料 pipeline 行為。

內容由社團填寫時，`由社團填寫` 就夠了。不再補充它是自述、未驗證、未經獨立確認，或由社團自行負責。

**The No Redundant Provenance Rule.** 除非那個區分會實質改變使用者的判讀或行動，否則不加入「可核對」、「可追溯」、「已驗證」、「主辦來源」、「官方來源」、「自述」、「尚未驗證」、「僅供參考」這類措辭。有原始連結時，`原始來源` 這個標籤就足夠。

### No Defensive Disclosure

不為了預防而加入法律、資安、隱私或維運者免責聲明。預設避免的例子：`未經法律專業人士審閱`、`非正式法律意見`、`本站不保證資料正確`、`使用者應自行判斷`、`本站不負相關責任`。

一般網頁實作的技術後果——IP 傳輸、HTTP 標頭、DNS、CDN、快取與 referrer 行為——不寫進介面，除非該行為不尋常且對使用者有實質影響。

**The Reduction-Is-Reduction Rule.** 刪掉多餘資訊後不得用別的東西補回來：不新增輔助文字、tooltip、徽章、括號註記、警告圖示或說明副標。減少就是減少。

### Copy Hierarchy

決定什麼該進介面時，依序排：

1. 實際內容或值。
2. 目前可用的動作。
3. 相關日期或狀態。
4. 實質的警告或限制。

其餘一般都省略。

**The Material-Risk Exception.** 下列事項不得為了精簡而隱藏：資安、敏感資料處理、破壞性或不可復原的操作、非預期的第三方資料分享、付款或帳務、使用者資料遺失，以及法律要求的揭露。它們仍要講清楚，但只出現在使用者需要它的那一步。

### Copy Review

修改既有頁面時，在這次改動的介面表面內刪除不必要的對外文字，不藉機擴大成全站改寫或另一輪稽核。特別找：對顯而易見標籤的解釋、provenance 評論、稽核導向措辭、防禦性免責、推測性警告、實作細節、重複的中繼資料，以及只為了展示透明度而存在的文字。

問：**這段文字不在的話，使用者會有什麼不同做法？** 答案是「沒有」就刪掉。
