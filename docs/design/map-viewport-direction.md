# 地圖視域改進方向

- 狀態：**歷史提案；後續規格已實作。** 本文原估算保留，不是現況。現況以[活動地圖契約](../contracts/event-map.md)、[`DESIGN.md`](../../DESIGN.md) 與[元件與介面規格](./components.md)為準。
- **後續技術規格**：[地圖新介面技術落地規格](./map-viewport-implementation.md)。已確認首次開啟維持 fit，取代本文軸線 A 的固定可讀倍率；桌機採左欄探索／行程切換與條件式詳情覆蓋。本文保留為歷史提案，實作目標以新規格為準。
- **2026-09-09 驗證補註：下文保留原始提案脈絡，不可直接作為實作規格。** 已確認 CSS Module 覆蓋欄寬、倍率試算與可讀性推論需要修正；一般模式／導航模式的行程位置也須分開描述。請先讀[驗證與初步視覺概念](./map-viewport-validation.md)，其中的核對結果優先於本文原始估算。
- 對象：公開閱讀端桌機版（`app/event-map-app.tsx`、`app/globals.css`）
- 起因：桌機版地圖在筆電寬度下，預設倍率遠低於攤位號碼可辨識的尺度。

## 問題

「地圖太小」有兩個獨立的成因，需要分開處理。

### 一、版面：地圖可視區被 592px 的水平 chrome 與 219px 的垂直 chrome 夾住

| 來源 | 位置 | 佔用 |
|---|---|---|
| 左欄 `.filters` | `globals.css:19` | 248px 寬 |
| 右欄 `.rightRail` | `globals.css:19` | 304px 寬 |
| `.map-region` 左右內距 | `globals.css:24` | 40px 寬 |
| `.topbar` | `globals.css:13` | 72px 高 |
| `.toolbar` | `globals.css:18` | 58px 高 |
| `.map-region` 上下內距 | `globals.css:24` | 38px 高 |
| `.map-title` | `event-map-app.tsx:578` | 約 50px 高（CSS 推算，未實測） |

`.workspace` 的 `height:calc(100vh - 130px)` 把前兩項垂直 chrome 寫死在 CSS 裡。

其中兩塊是版面塌陷，不是設計：

- **`.topbar` 第二欄的空白。** 四欄 grid 的第二欄是 `minmax(200px,1fr)`，只放活動名稱，剩餘寬度全部變成空白；搜尋框又被 390px 封頂，所以視窗越寬洞越大。
- **`.map-title` 右側的空白。** `justify-content:space-between` 但只有一個子元素。CSS 仍留著 `.map-title p` 與 `.map-title p b`（連 760px 的 media query 都還在改它），markup 自 baseline commit 起就沒有對應的 `<p>`。

### 二、縮放策略：初始倍率等於「整館塞進畫面」

`calculateMapFitZoom`（`app/map-viewport.ts:16`）同時扮演三個角色：初始倍率、最小倍率下限、「重設」的目標。第二與第三個角色是[縮放契約](../contracts/event-map.md#縮放契約)明訂的，第一個不是——它只是 `event-map-app.tsx:198` 那個 effect 的副作用。

後果是**預設看到的就是最不可讀的那一個倍率**。契約規定 145% 起才顯示社團縮圖；整館倍率離這個門檻差一個數量級。

## 這兩個成因的相對重要性

`fit = min((viewportWidth − 72) / floorWidth, (viewportHeight − 72) / floorHeight)`，`floorHeight` 固定 950，`floorWidth` 由 layout 長寬比推導（`event-map-app.tsx:130`）。

因此**寬度綁死倍率，直到地圖可視區的長寬比超過場地圖的長寬比為止**。1440×900 筆電上，可視區是 848×682（長寬比 1.24），FF47 的場地圖明顯比這個寬。

以場地圖長寬比 1.47 估算（由截圖推得，正式數字應從已發布的 `map.json` 讀 `layout.width / layout.height`）：

| 情境 | 可視區 | fit |
|---|---|---|
| 現況 | 848 × 682 | 56% |
| 只回收垂直 chrome | 848 × 828 | **56%（不變）** |
| 只讓右欄不佔位 | 1192 × 682 | 64% |
| 兩者都做 | 1192 × 828 | 80% |

**回收垂直空間在筆電寬度下單獨做等於沒做。** 它要等右欄讓出 304px、寬度不再是瓶頸之後才開始有價值，屆時貢獻 16 個百分點。這推翻了「先做低風險的垂直回收」這個直覺順序。

而 80% 仍在 145% 縮圖門檻之下——**版面回收再徹底也到不了可讀尺度**。要達到，只能改初始倍率。

## 外部參照

[Comike WebCatalog 地圖功能紀錄](../research/comike-webcatalog-map.md)（2026-08-06）記錄了功能面；2026-09-09 的補充觀察集中在版面。數字為 `getBoundingClientRect` 實測，視窗 1706 × 842 CSS px：

- 地圖頁沒有側欄，地圖全出血到視窗左右緣與底緣，無內距、無圓角、無邊框、無底色留白。
- 垂直 chrome 只有兩列：搜尋列 65px、導覽列 40px，合計 **104px**。往下捲時搜尋列捲走、導覽列黏頂（頁面可捲動量 56px）。
- 地圖容器 **1691 × 794**，即視窗寬的 99.1%、高的 94.3%。少掉的 15px 是捲軸。
- 活動日與場館切換是**疊在地圖左上角的浮動膠囊**，地圖內搜尋框同樣是浮動的，佔用版面高度為 0。
- 地圖上方沒有標題列，場館名稱在浮動膠囊裡。
- 詳情面板**推擠**而非覆蓋：面板開啟時地圖縮到 1186px（面板約 505px），關閉後整個消失、地圖長回 1691px，不留空狀態佔位。
- 綜觀交給右上角 minimap（160 × 86）。
- 互動實測：滾輪縮放正常（同一張圖磚螢幕寬度 64px → 256px）；拖曳平移 1:1 跟手，實測位移 (−435, −239) CSS px 與滑鼠位移完全相符，無慣性、無延遲。

[ADR-0001](../adr/0001-adopt-webcatalog-patterns-selectively.md) 界定的採納範圍是資訊架構、地圖定位、收藏模型與來源呈現，**不含版面與視域**。本文的軸線 B 與 C 若定案，等於把採納範圍擴張到第五類，需要新的 ADR 明說。軸線 A 不觸及該 ADR 的任何「不採納」項目——它不引入圖磚、不引入付費牆。

## 三條軸線

彼此獨立，可分別推進。

### 軸線 A：初始倍率與 fit 脫鉤

`calculateMapFitZoom` 保留最小倍率下限與「重設」目標兩個角色，**取消它作為初始倍率的角色**。初始改為固定的可讀倍率，並定位到使用者關心的位置（當日行程第一站、收藏、或 URL 帶入的攤位；都沒有時定位到場地圖中心）。

- 契約影響：[縮放契約](../contracts/event-map.md#縮放契約)需新增一條初始倍率規則。既有的「最小倍率是動態下限」「重設回到完整可用範圍」「選取後只移動不改倍率」三條都不變。
- 改動範圍：`event-map-app.tsx:198-221` 的 effect。
- 風險：使用者初次開啟看不到全場，可能失去空間脈絡。緩解是「重設」按鈕已經在地圖上且回到 fit；若實測仍不足，才進入軸線 A2。
- **A2（後續，需先推翻契約的「目前不做」）**：加入 minimap。契約已規定 minimap 必須與主地圖共用同一 layout 投影，不建立第二份座標資料。

### 軸線 B：垂直 chrome 從 219px 降到約 72px

1. 刪掉 `.map-title` 整塊。場地名稱 topbar 已有，展區由左欄 segments 的 active 狀態表達，這一列不提供新資訊。順帶刪掉 5 條沒有對應 markup 的 `.map-title p` CSS。
2. 刪掉 `.toolbar` 整列，日期與展區改為疊在 `.map` 左上角的浮動膠囊。`.route`（`globals.css:25`）已經是這個形狀的浮層，樣式可直接沿用。
3. `.map-region` 內距、`.map` 的 1px 邊框與 12px 圓角、cream 底色留白全部移除，地圖貼齊 workspace 邊界。
4. `.workspace` 的 `calc(100vh - 130px)` 隨之改為 `calc(100vh - 72px)`。

- a11y 必須處理：`.map-title` 的 `<h1>` 是這個畫面唯一的 h1。刪除時要把 topbar 的活動名稱升為 `h1`，或保留 sr-only 標題。
- 文件影響：[元件與介面規格](./components.md)的 Cards / Containers 與 Elevation 規則涵蓋浮動膠囊；地圖去除邊框與圓角需在該文件更新。
- **依賴軸線 C。** 單獨做在筆電寬度下不改變倍率。

### 軸線 C：右欄從常駐欄改為條件式

右欄目前在未選取攤位時顯示兩則空狀態（「選擇一個攤位」「還沒有安排攤位」），卻固定佔 304px。1050px 以下已經有「右欄變地圖右側浮層」的行為（`DESIGN.md:183`、`globals.css:28`），這是把既有模式往上延伸，不是新互動。

但不能照抄 Comike：它沒有常駐行程的等價物（お気に入り是獨立分頁），本專案的「當日行程列表」是常駐需求。所以需要先決定行程面板的歸屬——維持常駐欄、收成浮層、或併入左欄——這個取捨才是軸線 C 的實際內容，欄寬只是結果。

- 文件影響：`DESIGN.md:183` 明文描述桌機三欄工作區，改動需要新 ADR。
- 契約影響：[活動地圖契約](../contracts/event-map.md)的使用者流程第 4 點提到「開啟同一份社團資料的地圖側欄」，側欄形態改變需同步。

## 分期與順序

| 期 | 內容 | 前置 | 需要的文件動作 |
|---|---|---|---|
| 1 | 軸線 A | 無 | 更新縮放契約 |
| 2 | 軸線 C | 行程面板歸屬定案 | 新 ADR；更新 `DESIGN.md`、地圖契約 |
| 3 | 軸線 B | 軸線 C 已完成 | 更新元件規格；ADR 涵蓋版面採納範圍 |

順序理由：軸線 A 改動最小、可獨立回退，而且直接命中「預設看不清楚」這個實際體感；軸線 B 在軸線 C 之前做沒有效果。

## 驗收方向

定案時再細化，先記下判準的形狀：

- 倍率：以已發布的 FF47 `map.json` 的實際 `layout.width / layout.height` 重算上表，並在 1440×900 與 1920×1080 兩個寬度實測 fit 與初始倍率。
- 可讀性：初始倍率下攤位代碼可辨識；縮圖門檻 145% 的行為不變。
- a11y：`AccessibleEventMapRenderer` 的鍵盤走訪與唯一 h1 在每一期後都成立。
- 行動版：760px 以下的底部工作面板行為不得因為桌機版改動而退化。

## 未決

- FF47 場地圖的實際長寬比未從 `map.json` 讀取，本文所有倍率是以 1.47 估算。定案前必須換成實測值。
- 行程面板的歸屬（軸線 C 的前置）沒有結論。
- 軸線 A 是否需要 A2（minimap）才成立，要等 A 實測後才知道。
- Comike WebCatalog 的預設倍率**尚未確認**。2026-09-09 兩次載入的觀感不同（帶 `wcid` 時像是定位到該攤位的可讀尺度，不帶時是整館概觀），但兩次測到的圖磚螢幕尺寸都是 64px，無法據此判定倍率有無差異；免費會員 3 分鐘配額用完，未能完成對照。軸線 A 目前**不依賴**這個外部先例——它的理由是本專案自己的 fit 倍率與 145% 縮圖門檻的差距——但若要引用 Comike 作為佐證，必須先補這次觀察。
