# ADR-0019：個資請求走維運信箱，功能問題走公開 issue

- 狀態：已定案（2026-08-20）
- 相關契約：[社團自助控制面契約](../contracts/circle-portal.md)
- 相關 ADR：[ADR-0018](./0018-retention-is-the-circles-choice.md)、[ADR-0020](./0020-self-service-deletion-reuses-the-existing-ownership-chain.md)
- 相關 issue：[#30](https://github.com/dekkmarsvin/tw_doujin_event/issues/30)

## 脈絡

[#30](https://github.com/dekkmarsvin/tw_doujin_event/issues/30) 的驗收條件之一是「使用者如何提出查詢、更正或刪除要求，以及營運聯絡窗口」。

本站目前**沒有任何對外的聯絡窗口**。issue tracker 是公開的 GitHub issues（[`docs/agents/issue-tracker.md`](../agents/issue-tracker.md)），那是唯一存在的溝通管道，而它的每一個字都是公開且被搜尋引擎索引的。

依 [ADR-0015](./0015-access-lifts-when-no-third-party-bytes-remain.md)，Access 閘控解除的那一刻 `/circle` 與 `/api/auth/*` 同時對外可達，本站從那一刻開始收集真實個人資料。窗口不能晚於那一刻。

## 決策

**兩個窗口，依請求的性質分流：**

| 請求 | 去哪裡 |
|---|---|
| 功能問題、資料顯示錯誤、bug 回報 | GitHub issue，公開透明 |
| 涉及個人資料的查詢、更正、刪除 | 維運信箱 |

### 為什麼刪除請求不能走公開 issue

因為那會把請求變成它的反面。一封「請刪掉我的資料」通常同時交出信箱、社團身分，有時還有理由；走公開 issue 的結果是**這些內容成為永久公開紀錄**，而且比原本那筆資料更容易被搜尋到。用刪除換取更大的曝光，沒有人會同意這個交換。

而且它撤不回來。GitHub issue 關閉後仍然公開；刪除後仍可能留在 API 回應、第三方鏡像與已寄出的通知信裡。**公開的地方不能當成受理刪除的地方。**

反過來，功能問題留在公開 issue 是好事：其他人看得到、可以補充、可以驗證修好了沒有。這個決策不是把溝通關起來，是把**唯一不該公開的那一類**移出去。

### 四個約束

**一、信箱位址要出現在使用者看得到的地方**——隱私告知與 `/circle`，不是只寫在 repo 裡。寫在 repo 裡的窗口對不讀 repo 的人等於不存在。

**二、信箱不是個人信箱。** 它會印在公開文件上，並且必須在人員變動之後仍然可達。

**三、誤走公開 issue 的請求，先止血再處理。** 回覆導向信箱，請對方不要在 issue 內貼個資；已經貼出的由管理者編輯移除，並且知道**編輯歷史仍然存在**——移除是降低擴散，不是回復原狀。

**四、走信箱的請求要能確認是本人。** 一個宣稱來自某社團的刪除要求，若不驗證就執行，就成了任何人都能驅動的刪除按鈕。驗證沿用既有的擁有權鏈，見 [ADR-0020](./0020-self-service-deletion-reuses-the-existing-ownership-chain.md)。

## 這個決策沒有解決什麼

- **它不決定位址本身、回覆時限，也不決定要不要做表單。** 位址與時限在隱私告知定案時一起寫；沒有時限的窗口等於沒有窗口，但那個數字屬於 [#30](https://github.com/dekkmarsvin/tw_doujin_event/issues/30) 的營運決定。
- **它不取代自助操作。** 能在控制面自己完成的事就不該需要寫信；信箱處理的是自助做不到、或當事人已經無法登入的情況。

## 後果

- **多一個要有人看的收件匣。** 這是實質的營運負擔，而且它沒有 SLA 就等於不存在。
- **這個信箱與寄送登入信的設定是兩件事。** 登入信由 Mailgun 寄出，收件窗口是給人讀的地方；把它們混成同一個位址，會讓退信與自動回覆流進登入信流程。
- **公開 issue 的正當性反而更清楚了。** 分流之後，issue 裡出現個資就是一個要處理的事件，而不是一個模糊地帶。
