# ADR-0052：代表圖檢查的是「這是不是圖片」，不是「這是誰的主機」

- **狀態**：Accepted
- **日期**：2026-09-08
- **部分取代**：[ADR-0017](./0017-thumbnails-are-self-hosted-with-external-urls-kept.md) 的主機允許清單（本站代管為主線的決策不變）
- **相關文件**：[社團自助控制面契約](../contracts/circle-portal.md#媒體安全)、[資料傳輸與離線契約](../contracts/delivery-and-offline.md#快取標頭)

## 背景

外部圖片網址限於七個主機的允許清單。清單存在的理由是真的：讀者的瀏覽器會向那個主機發出請求，因此每個被允許的主機都拿得到讀者的 IP 與正在看哪一頁。

但社團手上的圖幾乎都不在那七個主機上。實際發生的事是：社團貼上自己的圖床網址，被拒絕，訊息告訴他們可以改用 Google Drive 或 imgur——也就是要他們先把圖搬到別人的服務，才准填。代表圖因此形同不可用，而不可用的欄位不會保護任何人，只會讓場刊少一張圖。

同時，允許清單根本擋不到它想擋的東西：`drive.google.com` 與 `i.imgur.com` 任何人都能上傳，要拿一個會記錄 IP 的網址，走允許清單內的主機就辦得到。

## 決策

### 1. 移除主機允許清單，寫入驗證只留協定

`THUMBNAIL_HOST_ALLOWLIST` 與 `isAllowedThumbnailHost` 刪除。代表圖網址的規則變成與外部連結相同：必須是 `https:`。`javascript:`、`data:` 與 `http:` 仍然拒絕——那條擋的是頁面本身被降級或被注入，與主機是誰無關。

### 2. 改檢查「這個網址真的是圖片嗎」，由瀏覽器回答

編輯器把網址放進 `<img>`；載得出來就顯示預覽，載不出來就擋住送出並說明原因。這是唯一在本站可行、又真的對應作者意圖的檢查：伺服器端要回答同一個問題就得代替使用者去抓那個網址，那反而讓本站變成任何人都能驅動的抓取器。

這個檢查擋的是打錯字、貼到網頁而非圖片、以及防盜連——也就是實際會發生的失敗。它不是安全邊界，繞得過；安全邊界是協定規則與撤下機制。

### 3. CSP `img-src` 跟著放寬成 `https:`

`public/_headers` 三條規則的 `img-src` 改為 `'self' data: https:`。這是**取捨的代價，不是附帶效果**：讀者的 IP 會暴露給社團挑的任何圖片主機。接受它的理由是代表圖對讀者的價值，以及允許清單本來就擋不住有意收集 IP 的人。`tests/circle-overrides.test.mjs` 改為斷言 CSP 與驗證器接受同一組位址。

### 4. 濫用改由事後處理

有問題的主機日後以黑名單處理，不預先列白名單。撤下路徑已經存在：管理者可撤下任何社團補充資料，`maintain@kotoban.top` 是爭議入口。

## 後果

- 社團可以直接使用自己的圖床，代表圖成為真正可用的欄位。
- 讀者瀏覽某個社團時，IP 會被該社團選擇的圖片主機看到。這是本 ADR 明知並接受的取捨。
- 本站代管（`media.kotoban.top`）仍是建議路線，也仍是唯一不會外洩讀者 IP 的路線；ADR-0017 的雙線結構不變。
- 黑名單尚未存在。第一次真的需要它時再建，屆時它的權威位置與 CSP 的關係要一起決定。

## 未決

- 是否在儲存時由 Worker 對該網址做一次 `HEAD` 驗證。目前不做：它增加一個對外請求、擋不住之後才換內容的主機，而且失敗時難以與暫時性網路問題區分。
