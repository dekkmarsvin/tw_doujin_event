# ADR-0010：社團身分改用配發的流水號

- 狀態：提案（尚未實作）
- 取代：[ADR-0003：社團身分以試算表主資料列為準](./0003-circle-identity-from-workbook-row.md)
- 相關契約：[社團目錄契約](../contracts/circle-catalog.md#社團身分規則)、[收藏與走訪規劃契約](../contracts/planning.md#儲存與版本)、[社團自助控制面契約](../contracts/circle-portal.md)

## 脈絡

[ADR-0003](./0003-circle-identity-from-workbook-row.md) 解決的是真問題：同一個社團的多個攤位必須共用一筆 `CircleRecord`。它選的解法是把身分**從內容推導**出來：

```
CircleRecord.id = `ff47-${FNV-1a(試算表列號 + "\0" + 社團名)}`
```

這個選擇的代價一直都寫在文件裡，但分散在三個地方，看起來像三件小事：

1. **`npm run claims:check` 這個腳本整個是為它而存在。** 它的檔頭註解直說：「inserting a row upstream or renaming a circle re-ids everything below it」。上游插入一列，其後所有社團的 ID 全變。
2. **`circle_claims` 有三個補救用欄位**——`circle_name_key`、`circle_name_at_claim`、`source_row_at_claim`。schema 註解稱它們為 recovery breadcrumbs，存在的唯一理由是 `circle_id` 會漂移，漂移後需要靠當初記下的名稱把認領接回去。
3. **[ADR-0007](./0007-circle-name-is-not-circle-editable.md) 鎖死社團名稱**，三個理由之一是「名稱是 `circle.id` 雜湊輸入的一半」。

把三者放在一起看，它們是同一個決定的三處疤痕：**身分被綁在會變動的內容上**。

還有一個更根本的錯位。ID 帶著 `ff47-` 前綴，也就是**身分是活動範圍的**。同一個社團明年參加 FF48 會拿到一個完全不同的 ID，去年的認領帶不過來——他們要重新認領一次。但社團不是每年重新誕生的東西；活動才是會結束的那一個。

用一句話說清楚錯在哪：**現在的模型是「社團名稱認領攤位」，應該是「社團認領攤位」。**

社團是持續存在的參與者，名稱是它的屬性，攤位是它在某一場活動的關係。把名稱和列號編進身分，等於宣稱換了名字就是換了一個社團。

## 決策

**社團身分改為配發的流水號，不從任何內容推導。**

```
CircleRecord.id = "c-000001"   // 配發序號，永不重用、永不重算
```

三條規則：

1. **不含活動範圍。** 序號屬於社團本身，跨活動延續。攤位由 `PlacementRecord` 以 `eventId` 表達，那才是活動範圍的東西。
2. **不從名稱、列號或任何可變欄位推導。** 改名、上游插列、資料重整都不改變序號。
3. **配發一次，永久保存。** 需要一份版本控制的登錄表記錄「序號 ↔ 目前的識別證據」；重新生成場刊時，比對出的是既有社團就沿用序號，比不到才配發新號。

登錄表（而不是工作簿）成為社團身分的來源。工作簿降級為**輸入之一**，與序號比對後併入。

這正是淘汰工作簿的前置條件：身分一旦不依賴工作簿，工作簿就可以逐步被社團自填的資料取代，而不會動到任何既有的收藏、行程與認領。

## 後果

### 直接獲得

- **`claims:check` 失去存在理由。** 重建場刊不再改變任何 ID，也就沒有漂移可查。
- **`circle_claims` 的三個 breadcrumb 欄位可以退役**（或降級為稽核資訊，不再是補救機制）。
- **[ADR-0007](./0007-circle-name-is-not-circle-editable.md) 的第三個理由消失。** 名稱不再是身分輸入。是否因此開放社團編輯名稱是**另一個決定**——前兩個理由（攤位比對鍵、縮圖索引 join key）仍然成立，需要各自解決後才談。本 ADR 不放寬 ADR-0007。
- **跨活動認領成為可能。** 社團認領一次，之後每場活動沿用；這是「社團認領攤位」該有的行為。

### 必須處理的代價

- **需要一個配號器與登錄表。** 公開閱讀路徑是靜態的、沒有資料庫，所以登錄表應是版本控制檔案（只增不改、不重排），由生成腳本讀寫。日後身分移入 D1 時，登錄表是遷移來源。
- **比對責任被顯性化了。** 現在「哪一列是哪個社團」由雜湊隱含決定；改用序號後，這件事必須明寫成比對規則，且會有比不到、比錯、一對多的情況要處理。**這不是新增的複雜度，是本來就存在但被雜湊藏起來的複雜度**——雜湊只是把「名稱變了就算不同社團」當成答案。
- **規劃資料需要 schema 3 遷移。** 使用者本機的收藏與行程存的是舊的雜湊 ID，必須以「舊 ID → 序號」對照表遷移，且照既有慣例**不得靜默清空**（見 [ADR-0003](./0003-circle-identity-from-workbook-row.md) 對 schema 1→2 的處理）。
- **D1 既有的認領與 override 需要同一份對照表遷移**，且必須在同一次操作內完成，否則會出現指向不存在社團的認領。
- **對照表本身要進版本控制並保存**，因為它是唯一能把舊資料接回去的東西。

### 不在本 ADR 範圍

- 序號的具體格式、配號器放在哪個腳本、登錄表的檔案格式。
- 比對規則的細節（何時算同一個社團、一對多如何人工裁決）。
- 是否開放社團編輯名稱——見上，那需要先解決攤位比對鍵與縮圖 join key。
- 淘汰工作簿的時程與步驟。本 ADR 只移除它作為**身分來源**的角色。
