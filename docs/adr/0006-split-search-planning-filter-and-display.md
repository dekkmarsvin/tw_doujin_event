# ADR-0006：把搜尋、規劃篩選與顯示設定拆成三組

- 狀態：已定案（2026-08-09 第一版實作完成）
- 相關契約：[搜尋、篩選與顯示設定契約](../contracts/search.md)

## 脈絡

`DisplayFilterControls` 當時掛在一個叫「**進階篩選與顯示**」的入口下，裡面只有五樣東西：收藏群組、行程狀態、結果排序、資訊密度、每筆媒體數量。

這五樣的共同用途是管理「我的規劃狀態」與「結果怎麼顯示」，**沒有一樣是在搜尋社團內容**。把它們放在名為進階搜尋的入口下，使用者會預期可以依作品、題材或標籤找社團，打開卻看到收藏管理條件。

當時的頂部自由文字搜尋把攤位代碼、社團名、作者、類別、作品、介紹與標籤串成一段文字查詢，因此能**偶然**搜到題材；但它沒有欄位範圍、主題候選、包含／排除條件、分級或原創／二創等結構化控制，也無法說明命中原因。

## 決策

依**責任**拆成三組，各自有自己的入口與規則：

| 組 | 責任 | 位置 |
|---|---|---|
| **搜尋**（探索 + 詳細） | 改變結果集合 | 搜尋頁；詳細搜尋採草稿後套用 |
| **規劃篩選** | 投影使用者規劃資料，不改寫社團或作品資料 | 行程頁 |
| **顯示設定** | 只改變順序或呈現密度，**不改變結果集合** | 行程頁 |

原「進階篩選與顯示」改名為「行程、收藏與顯示」，整組移至桌機與手機的「行程」頁。搜尋頁新增「詳細搜尋」，只呈現社團內容條件。

## 後果

- 已實作：創作者類型、作品名稱／題材（含浮動建議與跨語別別名）、原創／二創、明確 R18／一般分級，並寫入 `creator`、`work`、`workType`、`r18` 四個 URL 參數。
- **尚未實作**：多主題 AND／OR、排除主題、命中原因說明。契約已寫明它們仍缺，見[搜尋契約](../contracts/search.md#二詳細搜尋草稿後套用)。
- 搜尋投影必須在資料生成階段正規化。原始 `tags` 含尾端空白、逗號合併值與「R18, 一般」等複合字串，**在元件裡即時切割會切錯**。
- 分級不推測：未知與 R15 不得被當成一般或 R18。
- 顯示設定改變不得改變結果 ID 集合——這是可測的不變量，不只是原則。
