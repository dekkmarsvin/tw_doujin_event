# 配置圖自動辨識原型（Cloudflare Worker）

上傳主辦的配置圖（PNG／JPEG）與攤位清單，產生一份攤位 layout 草稿與 SVG 圖面。這是**獨立原型**：不接入主辦工作區、不取代 [地圖 authoring](../../docs/runbooks/map-authoring.md) 中既有的瀏覽器辨識 adapter，也沒有部署設定。

輸出是現行的 `EventMapLayout`（`app/event-map.ts`），回應前一律經過 `validateEventMapLayout`；座標為原圖像素，與[活動地圖契約](../../docs/contracts/event-map.md#地圖資料不變量)相同。

## 執行

```bash
npx wrangler dev --config prototypes/map-recognizer/wrangler.jsonc
```

開啟 `http://localhost:8787/`：選擇配置圖、貼上攤位清單（`A01~A22` 形式的範圍或逐一列出，排的順序以清單中第一次出現的順序為準），一張圖畫了好幾館時在預覽圖上框選其中一館，再按「辨識」。結果疊在原圖上，可下載地圖檔（layout）與 SVG。

也可以直接呼叫：

```bash
curl -F image=@plan.jpg -F boothList="$(cat booths.txt)" [-F crop=x,y,w,h] http://localhost:8787/recognize
```

回應含 `layout`、`report`（排的對應、編號方式、警告、驗證結果）、`svg`、`summary` 與各階段耗時。

## 做法

只假設台灣同人場配置圖共同的一件事：攤位是大量同尺寸的矩形，一格貼一格排成直線。其餘（排名、編號方向、場館外框）各主辦不同，交給攤位清單或人工。

1. **找格子**（`src/recognize.ts`）：兩種畫法各一道。格線圖（FF、PF、CWT、駁二）以「明顯長於數字高度的深色直線」為牆，牆圍起來的區域連同數字是一格；色塊圖（CH）以同色平坦區域為格，文字是填回的孔洞。兩道結果合併後，以尺寸群聚找出主要攤位尺寸；同一群內多數格子都寫了兩個上下排列的號碼時整群對半切開（CH20 的「01／02」）；少一面牆而黏在一起的連格按攤位寬度切回；一排中間缺一格且該處有文字時補上。最後把相鄰格子接成區塊並對齊共用邊。
2. **對應排**（`src/build-layout.ts`）：清單告訴每排有幾格。區塊依位置排出幾種走法（上下分帶或左右分欄、各兩個方向），以動態規劃把清單的排按順序對上攤位數相符（或差一、兩格）的區塊或同一直線上的區塊串，取對上最多的走法；一張圖有多館時，剩下的排再以另一種走法對一次。
3. **決定編號**（`src/glyphs.ts`）：不辨認數字本身。每種可能的編號路徑（起點角落、U 形折返或同向、是否補零）都會讓每一格「應該」寫某個號碼；正確的路徑會讓所有被說成「7」的字形長得一樣。先以各排自己的字形評分，再用整張圖學到的字形樣板重評，並以同一張圖多數排的編號規則作為旁證。某排比清單少格時，同一個比對會指出是哪個代碼沒畫。
4. **其他**：黑色實心方塊為柱子；紅色細箭頭為出入口（指向場內為入口）；大型色塊框成「未命名區域」待人工命名。名稱文字一律不做 OCR。

## 成本

- Worker 沒有任何 binding，不寫入、不呼叫外部服務；每次辨識只計一個請求加上解碼與辨識的 CPU 時間，一般配置圖在一秒內。`limits.cpu_ms` 設 5 秒上限，異常圖片不會無上限耗用。
- 以 [Cloudflare 成本基準](../../docs/runbooks/project-workflow.md#71-訂閱與計費基準查核日-2026-09-19)的 Workers Paid 內含額度（每月 3,000 萬 CPU ms）估算，每場活動幾十次辨識只占內含額度的極小部分；超出內含額度時才依官方 CPU 單價計費。
- 所有辨識都是純計算，同一組模組也能直接在瀏覽器分頁內執行（以 canvas 取像素），完全不經過 Worker。
- 沒有採用 Workers AI 或其他視覺模型：那是新增 Cloudflare 產品（[複雜度預算](../../docs/runbooks/project-workflow.md#74-複雜度預算)），按次計費，而且座標精度不足以直接產生攤位矩形。

## 限制

- **排名靠位置推定。** 攤位數相同的排（例如 FF47 的 B–V 都是 44 格）只能依走法決定是哪一排，送審前要核對排名；報告與頁面都會寫出採用的走法。主辦在同一館混用不同方向（例如同一館上下兩帶一左一右）時會對錯。
- **一張圖多館時要框選。** 各館共用攤位數時，整張圖一起比對會把館對錯；框選單館並給該館的清單才可靠，這也符合一份地圖對應一個「活動日 × 場地」。
- **不支援設計型地圖。** 攤位大小各異、以虛線分隔的活動導覽圖（例如只有少數大型攤位的企業展）只會找到零星格子。
- 不做 OCR：企業攤、舞台、特區名稱都要人工填寫；地標只框出大型色塊。
- 出入口只找紅色細箭頭；其他畫法需要人工新增。
- 圖片上限 700 萬像素、12 MB；不支援交錯（interlaced）PNG 與 WebP。

## 若要正式採用

部署一個新的 Worker 是新增常駐角色，依[擴充門檻](../../docs/runbooks/project-workflow.md#76-擴充門檻)需先由維護者決定；公開的上傳端點也需要存取控制（例如沿用主辦登入）。另一個選項是把 `src/` 的純計算模組直接放進主辦工作區的地圖編輯器，在瀏覽器內執行，不新增任何 Cloudflare 資源。
